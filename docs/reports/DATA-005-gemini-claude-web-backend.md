## 5. Found but not changed (Independent Review of DATA-004)

During careful review of the DATA-004 implementation in `scripts/generate_name_pool.py` and associated tests, the following bugs, subtle edge cases, and design limitations were identified:

### 1. Empty string run ID when `cache_path` is a flat filename
- **Location:** `scripts/generate_name_pool.py:567` (formerly `scripts/generate_name_pool.py:503` in `ab4e104`)
- **Code:**
  ```python
  all_run_ids = list(run_ids or [cache_path.parent.name])
  ```
- **Issue:** If `cache_path` is provided as a relative filename without parent directories (e.g. `raw.jsonl` or `Path("raw.jsonl")`), `cache_path.parent` evaluates to `Path(".")`, whose `.name` attribute is `""` (empty string). When `run_ids` is not explicitly provided, `all_run_ids` evaluates to `[""]`, producing an invalid empty string run ID in the output metadata JSON (`meta["run_ids"] = [""]`).
- **Recommendation:** Use `cache_path.resolve().parent.name` or fallback to a generated run ID / timestamp string if `cache_path.parent.name` is empty.

### 2. Live pre-flight cache check stamped `"generator": "live"` instead of `"deepseek"`
- **Location:** `scripts/generate_name_pool.py:1074-1078` (formerly `scripts/generate_name_pool.py:721` in `ab4e104`)
- **Code in `ab4e104`:**
  ```python
  if len(valid_names) >= target_names:
      print(f"Cache already contains {len(valid_names)} valid names (target: {target_names}). Building pool.")
      build_pool_from_cache(
          cache_path=cache_path,
          output_path=output_path,
          generator_kind=mode,
          ...
      )
  ```
- **Issue:** In DATA-004, when `run_generation_loop` is invoked in live mode (`mode="live"`) on a cache that already meets `target_names`, `build_pool_from_cache` was called with `generator_kind=mode`. This resulted in `"generator": "live"` being written into the pool metadata JSON, violating the schema expectation of `"generator": "deepseek"`.
- **Note:** Fixed as part of DATA-005 backend resolution in `scripts/generate_name_pool.py:1074-1078`, but noted here as a defect in original DATA-004 code.

### 3. `--build-only` unconditionally stamped `"generator": "deepseek"`
- **Location:** `scripts/generate_name_pool.py:1467` (formerly `scripts/generate_name_pool.py:1003` in `ab4e104`)
- **Code in `ab4e104`:**
  ```python
  built = build_pool_from_cache(
      cache_path=cache_path,
      output_path=output_path,
      generator_kind="deepseek",
      ...
  )
  ```
- **Issue:** The `--build-only` CLI branch hardcoded `generator_kind="deepseek"`. If an operator attempted to rebuild a pool from an offline-fake cache or any alternative backend cache, the resulting metadata falsely claimed the names were generated by DeepSeek.
- **Note:** Addressed in DATA-005 by inspecting cache entries to infer backend kind when `--build-only` is executed.

### 4. Plural pair heuristic only checks regular `-s` and `-es` suffixes
- **Location:** `scripts/generate_name_pool.py:511-514` (formerly `scripts/generate_name_pool.py:447-450` in `ab4e104`)
- **Code:**
  ```python
  if name.endswith("s") and len(name) > 1 and name[:-1] in pool_set:
      is_plural = True
  elif name.endswith("es") and len(name) > 2 and name[:-2] in pool_set:
      is_plural = True
  ```
- **Issue:** The filter only detects simple English plurals formed by appending `s` or `es`. In computer science terminology, irregular plural pairs and consonant+y plurals frequently occur:
  - `-y` to `-ies` (e.g., `query` / `queries`, `dependency` / `dependencies`, `proxy` / `proxies`)
  - Latin/Greek plurals (e.g., `matrix` / `matrices`, `vertex` / `vertices`, `automaton` / `automata`, `index` / `indices`)
  These plural pairs will evade detection and both appear in the final candidate pool.
- **Recommendation:** If strict deduplication is required for CS terminology, consider expanding the heuristic to check `ies` -> `y` and common irregular suffixes, or using an off-the-shelf lemmatizer if dependency policy permits.

### 5. `test_drop_reasons_fire` did not assert `corpus_overlap_embed`
- **Location:** `tests/test_generate_name_pool.py:147` (in `ab4e104`)
- **Code in `ab4e104`:**
  ```python
  # Also test embed_text overlap via candidate whose embed matches corpus
  # e.g., if corpus has "sorting_algorithm", its embed_text is "sorting algorithm".
  # A candidate matching that embed_text is filtered.
  filtered, n_raw, drop_counts = validate_and_dedupe_candidates(
      [fake_entry], corpus_nodes, corpus_embeds
  )
  assert drop_counts["corpus_overlap_exact"] == 2
  ```
- **Issue:** The test docstring and comments claim to test `corpus_overlap_embed` filtering, but the candidate intended to trigger embed-text overlap either matched `corpus_nodes` directly or did not trigger the embedding check. Consequently, `drop_counts["corpus_overlap_embed"]` was never asserted in `test_drop_reasons_fire`.
- **Note:** Claude added a separate standalone test `test_corpus_overlap_embed_drop_reason` later, but `test_drop_reasons_fire` retains misleading comments and lacks the assertion.

### 6. Unparseable responses cause divergent behavior between live loops and resume runs
- **Location:** `scripts/generate_name_pool.py:1296-1299` (formerly `scripts/generate_name_pool.py:840-843` in `ab4e104`)
- **Code:**
  ```python
  append_cache_record(cache_path, entry)
  if parsed:
      cache[(round_num, sf)] = entry
      subfield_collected[sf].extend(parsed)
  ```
- **Issue:** When an LLM produces an unparseable response (`ValueError`), `entry` (with `parsed_names=[]`) is appended to `cache_path` on disk, but `cache[(round_num, sf)]` is only updated in memory `if parsed:`. During an ongoing run, `needed_in_round` is only computed once per round, so the loop does not retry the failed subfield in that round and eventually increments `round_num += 1`.
  However, on a restarted/resumed run, `load_completed_cache` skips unparseable records from the disk cache. Thus, a resumed run sees `(1, sf)` missing from cache and attempts it, whereas an uninterrupted live run leaves it behind and moves to round 2.
